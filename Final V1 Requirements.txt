## 1. Product Definition

### Name

**MediaPulse**

### V1 Title

**MediaPulse — AI-Powered Movie Personality & Recommendation Engine**

### Core idea

MediaPulse asks a user a short series of questions about their movie taste, uses an AI model to interpret those preferences, creates a unique **Movie Personality**, and then uses that personality to retrieve relevant movies from **TMDB**.

The user ultimately receives a personalized **Movie Profile Card** containing their personality and recommendations.

---

The complete V1 experience should be:

The experience should feel like a polished product rather than a technical demonstration.

# 6. AI Personality Engine

This is the centerpiece of the project.

After the quiz is submitted:

```text
Quiz Answers
     ↓
Gemini
     ↓
Structured JSON
```

The AI should **not** directly return a random list of movies.

Instead, it creates a structured representation of the user's movie taste.

### Example output

```json
{
  "personaTitle": "The Midnight Mind-Bender",
  "description": "You gravitate toward atmospheric stories that challenge your perception of reality...",
  "preferredGenres": [
    "Science Fiction",
    "Thriller",
    "Mystery"
  ],
  "preferredThemes": [
    "Identity",
    "Reality",
    "Isolation"
  ],
  "pacing": "Slow Burn",
  "tone": "Dark and Atmospheric",
  "keywords": [
    "mind-bending",
    "psychological",
    "dystopian"
  ]
}
```

This distinction is important.

**Gemini interprets the user.
Our application controls the recommendation logic.**

That is a much better architecture for a portfolio project.

# 7. Dynamic Movie Recommendation Engine

Once Gemini produces the structured profile:

```text
Persona
   ↓
Recommendation Parameters
   ↓
TMDB API
   ↓
Movie Results
```

The application will query **TMDB**.

The result should contain approximately **5 recommended movies**.

Each movie should display:

* Poster

* Release year

# 8. Recommendation Quality

We should avoid simply searching TMDB using the AI-generated title.

Instead, we'll build a controlled recommendation pipeline.

For example:

```text
User:
Dark + Psychological + Slow Burn
             ↓
Gemini:
Sci-Fi + Thriller
Psychological
Dystopian
             ↓
Application:
Validate parameters
             ↓
TMDB:
Discover movies
             ↓
Application:
Filter / rank results
             ↓
Top 5 movies
```

This gives us room later to improve the recommendation algorithm without changing the AI system.

The result page should contain:

**Take the Quiz Again**

This should reset the quiz state and allow the user to generate another personality.

No account should be necessary for V1.

---

# 12. No Login System in V1

I strongly recommend **no authentication**.

That means:

❌ Google login
❌ GitHub login
❌ Email/password
❌ Auth database

For this product, authentication doesn't provide meaningful value yet.

Removing it means:

* Less code
* Fewer security concerns
* No authentication provider
* No database
* Faster development
* Better alignment with our $0 requirement

---

# 13. No Database in V1

Likewise, **we don't need a database initially**.

The user's session can exist entirely in the browser.

```text
Browser
  │
  ├── Quiz answers
  ├── Generated personality
  └── Recommendations
```

If we eventually decide that persistent profiles are valuable, that becomes a V2 consideration.

# 15. Security Requirements

This is non-negotiable.

API keys must **never** appear in:

* React client code
* GitHub repository
* public JavaScript
* `.env.example`

We'll use:

```text
.env.local
```

for development.

Example:

```text
GEMINI_API_KEY=...
TMDB_API_KEY=...
```

And:

```text
.env.local
```

will be included in `.gitignore`.

We'll commit:

```text
.env.example
```

containing only placeholders:

```text
GEMINI_API_KEY=
TMDB_API_KEY=
```

# 16. Cost Requirement — $0

This is now an explicit V1 requirement.

### We will prioritize

* Open-source libraries
* Free developer tiers
* Free hosting
* Client-side processing where practical
* No paid SaaS
* No unnecessary infrastructure

### We will NOT assume

> "It's free because someone said it has a free tier."

When we reach an external service, we'll verify its current free-tier terms before making it part of the architecture.

If something becomes paid or restricted, we'll look for a replacement or redesign that portion.

# 17. Error Handling

The application should gracefully handle:

### Gemini failure

```text
We couldn't analyze your vibe right now.
Please try again.
```

### TMDB failure

```text
We created your movie personality,
but couldn't retrieve recommendations.
Please try again.
```

### Invalid AI response

The server validates Gemini's JSON before using it.

### API rate limits

The UI should provide a friendly retry mechanism rather than exposing raw API errors.

### Missing images

Use a proper fallback poster rather than broken image elements.
